# TOPIK Database — 차기 회차 PDF 추출 및 다회차 DB화 계획

작성 기준: 2026-10-09. **계획 문서이며 구현·운영 DB 수정·배포 승인 아님.**

## 1. 대상 및 경계

- **첫 대상:** 제36회 TOPIK I B형 (`036-I-B`), 듣기 1–30번 + 읽기 31–70번.
- 그다음: 같은 파이프라인으로 37회 TOPIK I를 재검증하고, TOPIK II는 쓰기/정답 체계가 다르므로 별도 어댑터를 설계한다.
- **완료된 제35회 TOPIK I B형(`035-I-B`)은 변경 금지.** 중앙 PostgreSQL의 70개 `verified`, 30개 대본 `verified`, v4 blind audit, 수정·검수 이력 및 Stage-10 SQLite 동결 자료를 보존한다.
- 원본 PDF/MP3는 각 장치 로컬에 유지. 인증서·연결 정보 및 백업은 Git 외부 `TopikDatabase-runtime/`에 보관. 생성되는 추출 결과·이미지·본문/정답도 공개 Git에 올리지 않는다.
- **이번 목표는 문제/선택지/정답/배점/그림/지문·지시문을 정확히 DB화하는 것.** 듣기 대본은 원본과 대조해 연결하되, MP3 재생/구간 타이밍·클립 검증은 별도 단계다.

## 2. 실제 보유 자료와 위험

`topik-past-papers/36th/`에서 확인한 주요 로컬 자료:

| 자료 | 형태/확인 결과 |
| --- | --- |
| TOPIK I 합본 문제지 | 27페이지, 텍스트 추출 가능, 이미지 있음 |
| TOPIK I 듣기 문제지 | 8페이지, 텍스트 추출 가능 |
| TOPIK I 읽기 문제지 | 17페이지, 텍스트 추출 가능 |
| TOPIK I 정답표 | 2페이지, 듣기 30행 + 읽기 40행, 영역별 합계 각 100점 |
| TOPIK I 듣기 대본 | 12페이지, 텍스트 추출 가능 |
| TOPIK I 듣기 음원 | MP3 파일 보유(구간 검수는 이번 범위 밖) |

- 표지에 **제36회 / TOPIK I / B형** 표기 있음. PDF는 PyMuPDF/PyPDF로 선택 가능한 텍스트를 제공한다. PyMuPDF 추출은 한국어 띄어쓰기를 잃는 사례가 있으므로 pypdf와 상호 대조해야 한다.
- **36회 정답표의 읽기 번호는 `31–70`으로 인쇄**됨. 35회 정답표의 읽기 번호 `1–40`을 보정하던 규칙을 재사용하면 안 된다. 번호는 각 PDF에 인쇄된 영역/행을 기반으로 판단하고 중복·결측·범위를 차단한다.
- 그림이 포함된 문제와 페이지를 가로지르는 공통 지시문/지문은 글자만으로 복원하지 않는다. 이미지 payload/좌표·페이지·연결 문항을 별도 보존하고 시각 검수한다.
- 최초 원본의 SHA-256과 크기는 `manifest_early.json`의 36회 TOPIK I 네 종류와 대조한다. 분리된 듣기/읽기 PDF도 내용 교차 검증 자료로 사용한다.

## 3. 구현 순서

### A. 35회 보존 및 다회차 아키텍처 정비 — **첫 번째 필수 단계**

1. 중앙 PostgreSQL 전체 **백업과 별도 복구 가능성 확인**, 35회 문항/대본/정답/선택지/이미지/검수 기록/감사 이력의 회차별 기준 수치와 content fingerprint 저장.
2. 다회차 DB 모델(`exams`, `sections`, `questions` 등)과 동기화: 고유 식별자는 `036-I-B`, `036-I-L-001` … `036-I-R-070`, source/image/그룹/대본/감사 ID는 회차별 충돌 불가하도록 생성. `import_metadata` 키도 회차별 네임스페이스 적용.
3. **현재 UI는 `SELECT exams`가 정확히 35회 하나뿐이라고 검사**, 목록·bundle·media·질문 ID 정규식·공유 audio까지 `035`가 하드코딩되어 있다. 명시적인 `exam_id` 선택/필터를 도입하고 기존 기본값 `035-I-B`의 동작을 보존한다.
4. **현재 AI audit 35의 스냅샷은 일부 `source_files`/`question_groups`/`image_assets`를 전체 테이블에서 읽는다.** 36회 추가로 35회 과거 원본이 오염된 것처럼 보이지 않도록 모든 수집·읽기를 `exam_id`와 실제 참조 관계로 격리한다. 스냅샷 계약을 버전 관리하며 35회에 저장된 기존 v4 SHA를 사후에 덮어쓰거나 다시 기록하지 않는다. 추가 전후 35회 데이터의 별도 canonical fingerprint가 동일한지 회귀 검증한다.
5. 35회 전용 `pilot_35.py`, `migrate_sqlite_to_postgres.py`의 **빈 DB 전제**를 중앙 DB 추가 수단으로 재사용하지 않는다. 새 회차 전용 staging/append 경로로 분리한다.

**통과 기준:** 35회 read-only 문항 조회·검수·감사 히스토리와 이전 상태가 그대로이고, 두 회차를 지정해도 조회/필터/URL/이미지 출처가 혼합되지 않는다.

### B. 원본 입력 계약 및 PDF 분석

1. 합본/분리본 문제지·정답표·대본 파일명, SHA, 크기, PDF 페이지, 회차/급수/책형을 read-only로 확인해 36회 source manifest를 만든다.
2. PDF 페이지를 이미지로 렌더해 텍스트 추출 결과와 좌표(블록/스팬/글자/이미지 영역)를 비교한다. 가능한 곳은 pypdf 원문 띄어쓰기와 PyMuPDF 좌표를 함께 이용하며, 실제 레이아웃이 기준이다.
3. 원본/표지·예시 문항·문항 텍스트·인쇄 페이지·영역별 번호·공통 지시문/공통 지문·그림(선택지/본문)을 식별하는 일차 분석 보고서 생성. 불확실 문항은 `needs_manual_review` 및 구체적 warning으로 남긴다.
4. 35회에서 경험한 `고르 십시오`, 괄호 앞뒤 공백, 이미지 내 정답 선택지, R059 같은 분리된 줄 문제를 공통 회귀 예제로 보존하되 **36회 원문에 35회 보정 문자열을 무조건 적용하지 않는다.**

**통과 기준:** 사용 가능한 모든 페이지에 원본 해시와 page mapping이 붙고, 이미지/지문 누락과 텍스트 추출 실패가 정리된 예외 목록에 나타난다.

### C. 재사용 가능한 PDF → 중간 데이터 추출기

1. 코드 구조를 회차 독립적인 `sources`/`paper_parser`/`answer_parser`/`transcript_parser`/`normalizer`/`validator`/`staging_importer`로 분리하고, 36회별 레이아웃 규칙은 작은 명시적 어댑터로 만든다.
2. 우선 PDF에서 `question`, 4개 `choices`(그림 문항은 빈 텍스트 선택지 가능), `group_instruction`, `group_passage`, `points`, `printed_page`, `source_pdf_page`, `answer_key_number`, `images`를 구조화한다. **원문/정규화문을 각각 보관하고 필드별 출처 파일·페이지/좌표·추출기 버전**을 기록한다.
3. 대본 PDF에서는 듣기 1–30의 텍스트, 발문 출처와 서로 공유하는 대화 여부를 추출해 연결한다. MP3 원본은 SHA/논리 경로로만 등록하고 구간 시각·음성 일치를 추정하지 않는다.
4. 출력은 재현 가능한 회차별 **Git-ignored staged JSON 및 사람이 볼 수 있는 검수 미리보기**. 원본/답안/대본에서 발견한 정보 외에는 자동 채워 넣지 않으며 불확실할 때 fail-closed 처리한다. 텍스트 이미징 OCR은 필요한 페이지에서만 별도 원본 검증 이후 사용한다.

**통과 기준:** 70개 고유 문항과 영역·그룹·그림 연결이 형식/순서/좌표 검사를 통과하고 같은 입력으로 항상 같은 정규화 결과와 해시가 나온다.

### D. 정답·배점 독립 대조 (36회 특화 중요 관문)

1. 정답표를 문제지 파서와 **독립적으로** 읽는다. 1페이지 `듣기 1–30`, 2페이지 `읽기 31–70`을 각각 정확하게 파싱한다(35회식 읽기 +30 오프셋 금지).
2. 정답은 `①②③④` → 1–4로 정규화하고 문항 번호·영역·배점을 엄격히 매핑한다. 각 영역의 **30/40행, 정답 70개, 중복 0, 듣기 합계 100점·읽기 합계 100점** 조건을 강제한다.
3. 문제지에 인쇄된 배점과 정답표 배점, 선택지 1–4 존재와 정답값을 대조한다. 서로 다른 합본/분리본 PDF 정보가 모순이면 해당 문항은 적재 차단 후 근거와 함께 수동 판정한다.

**통과 기준:** 공식 PDF 정답·배점 70/70 일치, 누락/중복/범위 오류 0; 불일치 1개라도 있으면 production import 금지.

### E. 격리된 staging → 중앙 PostgreSQL 추가

1. 원본 35회에는 쓰지 않는 **임시 staging 데이터**에서 DB FK/CHECK/UNIQUE, row 수, 70개 문항·70정답·선택지 슬롯 280개·30대본·그림 참조, audit source link, 문자 인코딩/페이지 및 ID 검증.
2. `--dry-run`이 기본이며, 실제 반영은 명시적인 `--apply --exam 036-I-B`로만 실행. 외부 백업 및 35회 기준선 확인 후 트랜잭션 하나에서 해당 회차만 insert. 36회가 이미 존재한다면 덮어쓰기나 중복 적재 대신 중단하고 diff를 제공.
3. 새로운 36회 문항/대본 상태는 모두 `needs_manual_review`. 정답표 기계적 정합성 확인과 문항 내용의 사람 승인 상태를 구별. 35회 상태/이력과 변경 없는 내용 fingerprint 확인.
4. 각 장치는 PDF/MP3를 로컬에 두며 DB에는 논리적 상대 경로, hash, 이미지는 필요한 BLOB만 보존. 범위/저작권 확인 없이 외부 클라우드·Git 원문 업로드 금지.

**통과 기준:** PostgreSQL에는 35회 + 36회가 공존하고, 35회 데이터 불변·36회만 pending·문항 총수 140(35회 70 + 36회 70)·복구 및 멱등 동작 PASS.

### F. 36회 검수 UI, 독립 감사 및 종료

1. UI에서 회차를 명시적으로 선택하고 36회 문제지/정답표/대본/이미지를 문항마다 나란히 확인. 35회와 같은 409 충돌 방지·검수 이력과 cache 정책 유지. 회차를 바꾸면 bundle 및 캐시를 분리/무효화.
2. 36회 전용 source-frozen blind audit pass 생성. 이전의 오류 목록·검수 승인·직전 AI 판정을 보여주지 않고 원본 PDF/정답/대본/이미지를 전수 독립 대조한다. 결과의 `clear`/`finding`/`uncertain`과 증거·source refs·run SHA를 기록.
3. 오류가 나오면 원본 페이지에 근거한 source-backed 변경 및 대상 문항 재검수, 필요 시 새 independent pass를 실행. 과거 감사 이력은 append-only로 보존.
4. 70/70 clear, finding 0, uncertain 0, 원본/정답/그림/대본 검증, 운영 DB snapshot 일치 및 사용자의 최종 승인 게이트를 충족할 때만 36회 **문제·텍스트 추출 완료** 처리. MP3 구간 완료와 혼동하지 않는다.

**통과 기준:** 36회 문제·정답·텍스트 검수 완료, 승인 이력/감사 근거 존재, 35회 불변, 두 회차 간 UI/SQL/API 격리 회귀 PASS.

## 4. 테스트 및 배포 게이트

- 단위: PDF 페이지/행 파싱·그룹/문항 경계·한글 띄어쓰기·정답 표기·이미지 crop·OCR 예외·대본 공유 관계·불확실성 처리.
- 통합: 다회차 SQL FK/유일성, duplicate import 차단, 롤백, 증거/해시 동등성, 사진과 그림 선택지, 35회 과거 감사 조회/verified 상태 불변.
- UI: 35 ↔ 36 전환 및 문항 ID/문제지 미디어 경로·cache 격리, 낡은 version 저장 409, 미검수 표시.
- 운영: 백업/독립 restore 실증, 리허설 DB 통과 후 중앙 운영 DB append, 실사 후 안정된 별도 커밋/인수인계. 문서·테스트가 통과하기 전까지 기존 35회 서버 코드/데이터를 즉흥 수정하지 않는다.

## 5. 사용자에게 보고할 필수 결과

1. 36회 입력 파일과 SHA·PDF 페이지·시험 ID/책형 확인 결과.
2. 문항/보기/정답/배점/대본/그림 추출 건수, 불확실·재검수 대상.
3. 35회 전후 불변 체크와 운영 DB 추가 insert/diff 결과.
4. blind 전수 감사 verdict, 사용자가 승인해야 할 예외, run/hash 증거.
5. 테스트 결과, Git 커밋, 운영 배포 여부, 별도 남는 음원 구간 작업.

**중요:** 이 계획만 작성하는 단계에서는 PDF 원본, PostgreSQL, SQLite 동결본, 코드 동작 및 검수 상태를 수정하지 않는다.
