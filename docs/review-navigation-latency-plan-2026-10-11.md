# TOPIK 검수 UI 문항 전환·승인 지연 개선 실행 계획 (2026-10-11)

## 0. 의도, 기준선, 적용 경계

**목적:** 35/36회 검수 중 이전/다음·목록 선택과 검수 승인 후 이동의 **사용자가 체감하는 대기**를 없애거나 최소화한다. 실제 DB 승인 완료 시점과 화면 전환 시점은 별개로 측정한다. 승인 기록을 미확정 상태에서 완료로 표시하거나, 다른 PC의 수정·과거 독립감수·미저장 초안을 덮어쓰는 성능 최적화는 허용하지 않는다.

기준 코드: `7bbcecc`, 브랜치 `feat/topik36-pdf-ingestion-20261009` (계획 작성 시 clean). 이미 구현된 기능을 새로 구현한 것처럼 설명하지 않는다.

- **이미 구현:** 70문항 `/api/questions-bundle`(gzip 지원)와 `detailsCache`/버전 기반 캐시 무효화; 캐시 있는 다음 문항은 `sendOptimisticApproval()`로 저장 응답 전에 화면 이동; 승인 ACK 간소화 `?fast=1`; PDF/MP3 canonical URL; 개별 PostgreSQL 승인 쓰기는 하나의 연결에서 미디어 확인 후 잠금/저장; `TOPIK_REVIEW_TIMING=1` 선택적 쓰기 계측.
- **미해결:** 첫 bundle 도착 이전 또는 이전 캐시 무효화 이후 `selectQuestion()`은 개별 GET을 기다림. 일반 승인 경로는 다음 문항 캐시가 없으면 `POST→ACK→다음 문항 GET`을 순차 대기. `loadList()`는 승인 후 비차단 호출이지만 원격 연결·SQL 부하 발생. `get_question()`은 여러 순차 SQL과 매 요청 신규 PG 연결을 사용. 같은 원본 PDF의 `#page=` 전환이 브라우저 렌더에 주는 영향은 미계측.
- **2026-10-11 원격 PG 읽기 전용 실측:** 35/36회 6개 개별 상세 `2.46~3.11초`(문항별 SQL 7~11회), 70문항 묶음 `2.38~2.62초`(SQL 약 9회), 각 `ReviewStore`의 연결을 포함한 생성에 약 `1.62초`. 작은 표본이며 HTTP/화면 전체 체감 p50/p95가 아니라 Python DB 경로 실측값이다. 승인 POST를 운영 DB에서 측정하지 않았다.
- **보호 범위:** 운영 PostgreSQL `topik`, 35회 동결 SQLite, 35/36 실제 검수 승인/이력/대본, 35회 이전 AI 스냅샷, 36회 사람 수정 `036-I-L-010`, 공유 대본 25/26·27/28·29/30, 원본 PDF·MP3/클립, SSH/TLS, `import_metadata`의 신규 `transcript-speaker:v1` 마커와 기존 36 v4→v5 마커. 36 v5→v6은 **미적용**이며 이 작업에서 적용하지 않는다.

## P0. 정확한 분해 계측과 회귀 기준선 — 구현 착수 전

1. 로컬 Chrome/Edge의 Performance/Resource Timing으로 클릭→문항 제목·입력 필드 갱신 시간, `POST` 발송→ACK, 이후 다음 `GET`, 목록/번들/AI 별 요청 소요, PDF iframe `load`/Range GET, 음원 `load`를 **별도 이벤트**로 수집한다. 본문·자격증명·원본 URL 토큰은 로그로 내보내지 않는다.
2. 서버에서 요청별 연결 생성/TLS·SSH 왕복, snapshot BEGIN, SQL 수·소요, 이미지/미디어 확인 SHA, 쓰기 잠금/commit 시간을 opt-in 구조화 시간 로그로 분리한다. `TOPIK_REVIEW_TIMING` 기존 로그를 재사용/확장한다. SQL 원문·민감 데이터는 출력하지 않는다.
3. 같은 장치·SSH 환경에서 35/36회 각각 **첫 진입(cold), 번들 완료 후(warm), 빠른 10문항 이동, 캐시 무효화, PDF 패널 열림/닫힘**을 여러 번 반복한다. 중앙값(p50)과 p95, 캐시 적중률, GET/POST 수, 마지막 문항·필터 순서 이동을 기록한다. 실제 승인 POST는 **운영에서 금지**; 별도 복제 PG+미디어 사본에서만 측정한다.

**산출물:** 전후 재현용 측정 스크립트/보고서, 기준선 JSON(개인 정보 없음). 체감 지연의 주범이 원격 연결/SQL인지 PDF 렌더인지 결정한다.

## P1. 프런트 우선 — 클릭과 화면 이동을 백엔드 대기에서 분리

대상: `src/review_ui.html`, `tests/test_review_ui_flow.py`, `tests/test_review_ui_multi_exam.py`, `tests/test_review_ui_media_urls.py`.

1. 기존 70문항 bundle를 **완료 즉시** 세션 캐시에 반영하되 초반 `list` 응답 이후에는 현재 문항과 다음 2~3개를 **우선 순위별 단건 프리패치**한다. bundle 대기 중에도 실제 클릭을 우선한다. 비슷한 여러 GET의 네트워크 폭주를 막기 위해 한 회차당 백그라운드 단건 GET 동시 실행 1~2개로 제한하고 같은 `(exam,id,version)` 요청을 합친다.
2. 문항 이동은 **최신으로 판단되는 캐시 데이터가 있으면 같은 이벤트 루프에서 즉시 렌더**한다. 캐시가 없으면 기존 검증된 GET fallback을 유지하며 `로딩 중`을 표시한다. 프리패치 실패가 승인·입력 UI를 막지 않도록 한다. `selectedId/requestId`, 회차 전환 generation, `bundleProtectedIds`, 서버 `review_version`/질문 버전 비교로 늦게 도착한 데이터가 최신 편집·승인 ACK를 덮어쓰지 못하게 한다.
3. **승인 후 이동:** 미저장 음원·공유 대본 변경이 없고 다음 문항 스냅샷이 안전하면 기존 optimistic 경로를 사용한다. 캐시 누락이면 독립적인 다음 문항 GET과 승인 POST를 **병렬로 시작**해 직렬 대기를 제거한다. 다만 다음 문항의 원본이 바뀔 수 있는 공유 대본 정정은 반드시 기존 짝 문항 검사/잠금/동의 경로를 유지한다.
4. 낙관적 승인은 `저장 중`으로만 표시하고, 정상 ACK 확인 후 `승인 완료`와 최신 버전으로 갱신한다. 409·서버 실패·ACK 유실·크래시에서는 완료로 표시하지 않고 전송 당시 입력과 이전 문항 ID를 `failedReviews/pendingReviews`로 보존하며 복구 경로를 제공한다. 실패한 POST 자동 재시도 **금지**. 기존 pending 수 4건 상한/전송 중 재진입 방지 유지.
5. ACK 이후 즉시 다시 호출하는 목록 GET은 이동 critical path에 넣지 않는다. 연속 승인에서 불필요한 중복 목록 새로고침은 모아서 실행하되, 다른 PC의 수정은 포커스 복귀·명시 새로고침·짧은 백그라운드 버전 재검증에서 감지한다. 오래된 캐시로 저장하려 하면 서버 원자적 CAS/409를 반드시 유지한다.

**P1 합격 조건:** 검증된 warm-cache에서 일반 이전/다음 클릭→입력 필드 갱신 `p95 ≤ 100ms` **목표**(실측 후 보정 가능). 연속 승인 시 화면 전환은 승인 ACK보다 먼저 시작하되 승인 최종 표시에는 성공 ACK가 필요하다. 오류·필터·음원 미저장·공유 대본·회차 변경 시 데이터 유실/가짜 승인 0건.

## P2. 서버 핵심 병목 — 신규 연결 및 순차 SQL 왕복 절감

대상: `src/database.py`, `src/review_ui.py`, Postgres 읽기/쓰기·동시성 테스트.

1. psycopg3의 유지보수되는 `psycopg_pool` 같은 **검증된 소규모 연결 풀**을 검토·선택한다. 동일 프로세스 DB URL 기준으로 읽기/쓰기 연결을 제한(초기 2~4개, 환경설정), 요청마다 독립 lease; 스레드에서 동일 트랜잭션 공유 금지. 반납 직전 rollback/reset·읽기 전용 상태 검사, 풀 고갈 timeout, 고장난 TLS/SSH 연결 폐기·재연결, 서버 종료 시 닫기를 시험한다. 기기별 reviewer 서버가 다르면 기기별 풀이다.
2. 기존 `get_question(fast=True)` 개별 조회 7~11 SQL 왕복을 가능한 부분부터 **2~4회 수준**으로 통합하는 방안을 검증한다. JOIN/CTE 또는 JSON 집계로 문제·보기·대본·현재 검수 버전·최근 이력·공유 대본 검사 데이터를 같은 `REPEATABLE READ, READ ONLY` snapshot에서 만든다. 구형 SQLite adapter와 35/36 결과 JSON 필드 parity 유지. 어려운 F3 감사·오디오 근거는 무리해서 없애지 않는다.
3. `get_questions_bundle()`의 70문항 batch는 유지하고, 하나의 snapshot 및 9개 SQL 순차 RTT 중 실제 비싼 쿼리만 최적화한다. 번들 크기·압축·가용성·버전 충돌 규칙 변화 없이 전후 p50/p95를 기록한다.
4. 승인 쓰기 트랜잭션의 원본 PDF SHA-256 검증, `FOR UPDATE`, 공유 대본 쌍 잠금 순서, `review_records` 원자적 저장, `question` CAS/409, `transcript-speaker:v1` 마커 버전 계산은 유지한다. 비동기 승인과 DB 연결 풀을 함께 켰을 때 순서 뒤집힘·deadlock·중복 저장을 별도 복원 PG로 시험한다.

**P2 합격 조건:** 동일 원격 네트워크에서 cold GET p50/p95가 기준선 대비 **의미 있게 감소**(우선 목표 50% 이상); SQL 횟수·연결 생성 수 감소가 수치로 확인됨. 미디어 검증 생략·다른 질문 데이터 혼합·풀 누수·stale-write 성공 0건. 개선이 없다면 풀/쿼리 변경은 롤백한다.

## P3. 미디어/렌더 지연 분리 — 필요 시에만

1. 같은 PDF를 사용하는 문항 간 실제 `iframe.src=#page=N` 전환 시 브라우저가 전체 PDF 또는 큰 Range 요청을 다시 하는지 계측한다. 초기 텍스트 표시가 PDF 렌더를 기다리지 않도록 유지하고, 필요한 경우에만 동일 출처 iframe 보존·페이지 전환 정책을 구현한다. 35/36 듣기/읽기 시험지의 서로 다른 원본 파일은 합치지 않는다.
2. `sourceWithSharedAudio()`가 보장하는 동일 MP3 `src` 유지 및 `player.load()` 중복 호출 방지를 실사용 브라우저에서 검증한다. 듣기 재생/시작 끝/검증 증거를 다음 문제의 값으로 오염시키지 않는다.
3. 현재 `/media`는 DB 조회 + 장치 로컬 파일의 크기/SHA 확인을 매 요청 수행하며 `no-store`를 사용한다. 무결성 확인을 삭제하거나 검증 전 내용 전송을 허용하지 않는다. 재검증 비용이 실제 지연 원인일 때만 원본 버전·SHA에 결합한 별도 안전 캐시 정책을 설계하고 음원/그림/문제지 변경 감지와 권리 제한을 먼저 검증한다.

**P3 합격 조건:** 단순 문항 이동에서 불필요한 전체 PDF/MP3 재전송 0건을 목표로 하고, 정확한 문항별 PDF 페이지·음원 재생·파일 검증을 유지한다. 실제 재전송이 없으면 P3 변경을 생략한다.

## P4. 격리 통합 시험, 배포, 성능 수용

1. 최신 운영 DB를 **읽기 전용 백업한 후** 독립 PostgreSQL에 복원하고, 별도 데이터베이스 URL과 원본 미디어 복사본을 사용해 실제 승인 POST를 시험한다. **운영 DB 승인/상태 변경 0건**. 시험용 DB 삭제 시 식별자와 백업을 확인하고 시험 DB만 정리한다.
2. 테스트 매트릭스: 35·36 × 캐시 hit/miss/bundle 늦게 도착 × 1개/연속/마지막 문항 승인 × 수정/메모-only/미수정 × 필터/정렬/회차 전환 × 실패/시간 초과/ACK 유실/409 × 두 PC 동시 편집 × 35 공유 대본 25/26·27/28·29/30 × PDF/MP3/음원 구간 미저장. DB 전후 대본·정답·이미지·원본·사람 승인 이력 해시/상태 비교. 과거 35 감사 해시와 현재 35 source hash도 구분해 보존.
3. `py -3 -B -m unittest discover -s tests -q` 전체 테스트 + 실제 브라우저 E2E(일반/320/390/1280 너비) + HTTP 무인증 차단/CSRF/원본 제한 + 과부하 테스트. 각각 이전 버전과 동일 조건 p50/p95, 클릭→렌더 시간, 승인 ACK 시간, 페이지/음원 재요청 및 fallback 빈도 비교.
4. P1→P2→P3를 **별도 커밋**으로 분리하고 단계마다 검증한다. 실제 사용 중인 localhost 서버는 열린 초안/저장 대기 여부를 확인하기 전까지 강제 종료·새로고침하지 않는다. 코드 배포 후 서버 프로세스를 재시작해야 서버 최적화가 반영된다. PC와 노트북 모두 갱신한 뒤 기존 포트·SSH/TLS·DB 연결 검증, 이상 시 이전 커밋으로 되돌린다.

**즉시 중단 조건:** 확인되지 않은 승인 성공 표시, 자동 재제출로 이력 중복, 원본/편집 초안 소실, 버전 오류 우회, 누락된 `speaker` revision, 공유 대본/음원 근거 혼동, 원본 파일 무결성 검증 약화, SSH/TLS 비활성화.

## 구현 우선순위 및 승인 단계

1. **P0+P1 먼저:** 캐시·다음 문제 요청 중복 제거/선행 로딩 및 승인 화면 이동. 체감 지연 해결이 주목적.
2. **P2 다음:** DB 연결 풀 + 쿼리 왕복 최적화. 미리 읽지 못한 문제도 빨리 불러오는 근본 개선.
3. **P3 조건부:** 실제 PDF/MP3 재전송이 측정될 때만 적용.
4. **P4 마지막:** 격리 승인/충돌 E2E 및 실측 비교 후 안전하게 배포.

**이번 요청의 범위는 계획 작성만이다.** 이 문서 생성은 기능 구현, 데이터베이스 쓰기, 라이브 검수 서버 재시작, Git push 또는 실제 성능 개선 완료를 의미하지 않는다.
