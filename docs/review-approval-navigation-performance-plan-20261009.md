# TOPIK 검수 승인 지연·자동 이동 오류 개선 계획 (2026-10-09)

## 범위와 목표

- 대상: `src/review_ui.html`, `src/review_ui.py`, `src/database.py` 및 관련 테스트. 35회·36회 검수 화면의 승인 흐름 모두 유지.
- **기능 목표**: 저장 성공 확인 시 사용자가 선택한 다음 문항으로 정상 이동하고, 이미 저장된 수정 내용을 '미저장'으로 오인하지 않는다. 실제 미저장 변경이나 불확실한 저장 결과는 버리지 않는다.
- **성능 목표**: 다음 문항 캐시 유무에 따른 체감 편차를 줄이고 원격 PostgreSQL 연결, PDF·MP3 반복 로드의 불필요한 비용을 제거한다.
- 범위 제외: 문제/정답/대본 내용 변경, 사람 검수 일괄 승인, 원본 PDF·MP3 수정, DB 스키마 변경·마이그레이션, 실제 운영 검수 POST를 통한 성능 테스트.

## 현재 확인된 근거

1. `src/review_ui.html:1560-1647`: 다음 문항 캐시가 없으면 승인 POST 응답을 기다린 후 `selectQuestion()`을 호출하지만, 성공 시 `state.baseline`을 갱신하지 않는다. `dirty()`·`canNavigate()` (`763`, `1031-1034`, `1065-1068`)에서 이미 저장된 수정/메모도 미저장으로 판정해 사용자가 이동 확인을 취소하면 승인된 현재 문항에 남는다. 실제 JS 함수 기반 모의 재현 완료. 반면 캐시가 있는 낙관적 경로는 `1521`에서 baseline을 갱신한다.
2. 현재 승인 이동은 `state.items` 전체를 기준으로 다음 문항을 고른다 (`1578-1580`, `1617-1620`). 활성 필터·위험도 정렬을 반영한 `state.visible` (`587-625`)과 어긋날 수 있다.
3. `src/review_ui.py:1511-1592` 승인 저장은 원본 증거 사전 검증용 읽기 연결, 잠금·저장용 쓰기 연결을 각각 새로 연다. `src/database.py:94,228`에서 원격 psycopg 새 연결을 생성한다. 로컬 SSH 터널로 읽기 연결 약 **1.7–1.8초**, `SELECT 1` 약 **0.48–0.53초**; 검수 HTTP GET 3회 중앙값은 문항 목록 **2.44초**, 상세 **3.56초**, 묶음 **3.60초**였다. 저장 POST 단계별 시간은 운영 DB를 변경하지 않아 미측정이다.
4. `src/review_ui.html:429-446,1213-1259`의 공유 PDF·MP3 URL 정규화는 35회에만 적용된다. 36회 듣기는 같은 약 **76,965,670바이트** MP3를 문항별 다른 URL로 재요청할 수 있다. 로컬 1KB HTTP Range GET 실측 **2.57–2.70초**; 읽기 PDF GET **2.29–2.48초**. `src/review_ui.py:1601-1640`은 미디어 요청마다 파일 SHA-256을 검증하고 `1749`는 `Cache-Control: no-store`를 설정한다.
5. `tests/test_review_ui_flow.py`의 기존 승인 테스트는 실제 `selectQuestion()`/`canNavigate()`를 통과하지 않는 mock이라 앞의 상태 오류를 탐지하지 못했다. 기존 9개 테스트는 통과했지만 해당 동작을 보증하지 않는다.

## 구현 순서 및 합격 기준

### P0. 승인 상태·자동 이동 버그부터 수정 (최우선)

**수정 후보:** `src/review_ui.html`, `tests/test_review_ui_flow.py`.

- 일반 승인 경로에서 **성공적이고 유효한 저장 ACK를 확인한 뒤** 제출한 스냅샷을 기준으로 baseline 및 상태를 일관되게 갱신한다. 저장 도중 추가로 바뀐 입력이 있다면 그 변경은 보존하고 무조건 덮어쓰거나 이동하지 않는다.
- 저장 실패, HTTP 409, 응답 유실, 불일치 ACK에는 기존 초안·버전·오류 안내·재확인 절차를 유지한다. 검증되지 않은 저장 결과를 승인 성공으로 표시하지 않는다.
- 다음 대상은 승인 직전 화면의 **가시 목록·정렬 순서**에서 결정해 필터 외 문항으로 갑자기 넘어가지 않도록 한다. 필터에서 더 이상 다음 항목이 없거나 마지막 문항이면 '더 이상 다음 문항 없음'을 안내한다.
- 음원 구간의 **실제 미저장 편집**이 있다면 승인만으로 버리지 않는다. 이동 보류와 명확한 안내를 유지한다. 기존 낙관적 승인 흐름의 `pendingReviews`/`failedReviews`/`committedReviews` 안전장치는 보존한다.
- 회귀 테스트: 다음 문항 캐시 있음/없음 × 수정/미수정/메모만 수정 × 승인/실패/409/응답 유실 × 필터/정렬/마지막 문항 × 음원 구간 변경. 실제 `dirty` + `canNavigate` + `selectQuestion`을 통과하는 Node VM·DOM 테스트를 포함한다.

**통과 조건:** 성공적으로 저장한 검수가 **가짜 미저장 변경 경고 없이** 의도한 다음 문항으로 이동하고, 실패·불확실한 저장이나 진짜 미저장 초안은 자동 유실되지 않는다. 35회·36회 모두 회귀 테스트 통과.

### P1. 36회 공통 미디어 중복 요청 제거 (고우선)

**수정 후보:** `src/review_ui.html`, 미디어 URL/응답 테스트.

- 실제 DB 원본 파일 식별을 확인해 36회도 공통 PDF·MP3를 **같은 회차·같은 원본 파일·같은 미디어 종류** 단위로 정규화한다. 듣기 시험지·읽기 시험지는 서로 다른 파일이므로 잘못 합치지 않는다.
- 동일 MP3를 다음 듣기 문항에서도 사용하면 `player.src`를 유지하고 `player.load()`를 다시 호출하지 않는다. 진행 중 재생, 확인한 구간, 음원 미저장 상태의 안전성을 점검한다.
- 동일 PDF는 문항마다 불필요하게 다시 다운로드·렌더하지 않고 페이지 전환만 한다. PDF 뷰어 동작·브라우저의 실제 네트워크 요청으로 확인한다.
- 기존 same-origin 제한과 회차 격리, 로컬 파일 SHA 검증을 유지한다. 캐시 정책이나 무결성 검사를 성급히 완화하지 않고 URL 정규화 효과부터 측정한다.

**통과 조건:** 동일 원본 파일을 사용하는 인접 문항 이동에서 **불필요한 미디어 재요청 0건**; 문항별 올바른 PDF 페이지 및 음원 연결 유지; 35회 정상 동작 유지.

### P2. PostgreSQL 연결·왕복 비용 최적화 (고우선, 별도 격리 테스트)

**수정 후보:** `src/review_ui.py`, `src/database.py`, PostgreSQL 연결·동시성 테스트.

- 먼저 요청 단계별 시간(연결 생성, PDF SHA 검증, 질문 잠금 대기, SQL 조회/쓰기, COMMIT, 클라이언트 ACK·다음 GET)을 **본문·자격증명 없이 시간 수치만** 계측한다. 운영 DB에서는 읽기 전용 진단으로 제한한다.
- 매 요청마다 여는 psycopg 연결을 줄이도록 **제한된 크기의 안전한 연결 풀/재사용**을 검토한다. 쓰기 트랜잭션의 rollback·반납, 스레드 간 연결 공유 방지, 연결 오류 복구, 유휴 제한, SSH 터널 재연결, TLS 검증 보존을 우선한다.
- 원본 검증은 폐지하지 않는다. 같은 안전 보장을 유지하면서 사전 검증의 DB 조회·중복 해싱 비용을 줄일 방법을 평가한다. 단순 파일 크기/mtime만으로 SHA 검증을 대체하지 않는다.
- 잠금 순서·`SELECT ... FOR UPDATE`·충돌 시 409·원자적 review_records/질문·보기·대본 저장, 36회 punctuation-marker 버전 +1 보호는 유지한다.
- 테스트는 **폐기 가능한 PostgreSQL**과 독립 파일 복제에서 수행하고, 연결 재사용 전후의 p50/p95 성능을 같은 환경·횟수로 비교한다. 운영 POST 계측은 사용자의 별도 승인 전 수행하지 않는다.

**통과 조건:** 연결 비용·GET 요청 지연이 기존 기준보다 **측정 가능한 수준으로 감소**, 연결 누수/쓰기 실패/트랜잭션 교차/동시 검수 충돌 없음. 수치 개선이 없거나 안정성 위험이 생기면 최적화 철회.

### P3. 통합 검증·안전한 릴리스

- 정적 검사, `py -3 -B -m unittest tests.test_review_ui_flow -q`, PostgreSQL 연동 테스트, **전체** `py -3 -B -m unittest discover -s tests -q`, `git diff --check`를 실행하고 오류가 있으면 수정한다.
- 실제 Chrome UI는 **독립 테스트 DB**에서 새로고침 후 테스트한다. 평상시 승인, 수정 후 승인, 저장 실패/409, 필터 변경, 마지막 문항, 다음 문항 미리 로드 여부, 35회·36회, 음원 로드 중 이동을 확인한다.
- 성능 기준: (a) 로컬 캐시가 있는 다음 문항의 **화면 이동 시점과 DB ACK 시점을 별도 기록**, (b) 캐시가 없는 경우의 전체 지연과 요청별 p50/p95를 **수정 전과 동일 환경**에서 비교, (c) 36회 공통 미디어 재요청 횟수 확인. 네트워크 편차가 크므로 단일 임의 절대시간을 보장하지 않는다.
- 변경은 단계별 소규모 커밋으로 분리하고 소스 PDF·MP3/운영 DB/35회 검수 이력은 불변으로 유지한다. 리뷰 서버 재시작·브라우저 새로고침 전 **열려 있는 편집 초안·미완료 승인**을 확인해 사용자에게 알린다.
- 릴리스 전의 명시적 중단 조건: 승인 여부가 불확실한데 성공으로 표시함, 입력 유실, 35회 회귀, PDF/MP3 원본 매핑 오류, DB 버전 경합·롤백 실패, SSH/TLS 보안 저하.

## 실행 경계와 다음 행동

이 문서는 **개선 작업 계획**이다. 계획 수립 단계에서 운영 승인 버튼 POST·DB 쓰기, 서버 재시작, Git push, 운영 배포는 하지 않는다. 구현 요청을 받으면 **P0만 우선 구현→검증→결과보고**하고, 합격한 뒤 P1, P2, P3 순서로 진행한다. DB 구조/실데이터를 바꿔야 하는 변경은 별도 사전 확인 대상이다.
