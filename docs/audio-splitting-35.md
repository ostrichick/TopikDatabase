# 제35회 TOPIK I 듣기 구간: 근거와 검수 기준

이 문서는 로컬 음원의 **구간 후보**, 수동 검증, 클립 내보내기의 차이를 기록한다. 원본
`35-TOPIK-I-Listening-Audio-File.mp3`는 수정하지 않는다. 자료의 공개·재배포
허가는 별도로 확인해야 한다.

## 실제 음원 분석 결과

`src/audio_35.py`의 읽기 전용 분석을 실행해 확인한 값:

- 음원 길이: **2,356,715ms**. 후보 검출에 쓰는 네 임계값(-30/-35/-40/-45dB)에서
  모두 긴 무음 31개가 관찰되었고 각 경계는 설정된 120ms 오차 범위에서 안정적이었다.
- 무음 분포를 바탕으로 **후보 클립 27개**, 문항 **30개에 대응할 수 있는 구간**이
  제안되었다. 1~24번은 개별 후보이며, 25·26 / 27·28 / 29·30번은 각 한 개의
  공통 대화 후보를 공유한다. 후보의 상태는 모두 `candidate_unverified`다.
- 위 대응 관계는 첫 긴 무음이 예시 뒤에 나온다는 **가정**에 의존한다. 무음 개수나
  임계값 안정성만으로 회차·문항 번호·대본 일치, 발화 시작과 종료, 응답 대기음의
  포함 여부를 입증할 수 없다. 숫자상 30문항을 모두 덮더라도 자동 승인할 수 없다.

현재 로컬 적용 결과: `py -3 src/prepare_audio_35.py`로 기존 DB를 백업한 뒤
`audio_segments`에 30개 문항의 미확정 경계를 연결했다. 이후
`py -3 src/export_audio_candidates_35.py`로 실제 MP3 후보 27개를
`topik-past-papers/derived/audio-candidates/`에 출력했다. 1~24번은 개별
파일이고 공통 대화 세 쌍은 쌍별로 한 파일이다. `manifest.json`에는 각
파일의 문항 번호·시각·파일 해시가 저장되어 있다. 원본은 변하지 않았으며,
파생 MP3 파일명에 `CANDIDATE-UNVERIFIED`를 명시했다. 파일의 내용은
청취 검수 전에 확정하지 않는다. 수동 검증된 MP3는 별도로
`topik-past-papers/derived/audio-clips/`에 내보낸다.

## 데이터와 API 계약

- 원본 MP3의 SHA-256과 길이를 등록하고, 문항별 `audio_segments`에
  `start_ms`, `end_ms`, `status`, `version`, `source_sha256`을 보관한다. 후보
  등록 전에는 구간이 없는 `null` 상태이며, 현재 35회 시범 DB에는 30문항 전부
  `candidate`로 등록되었다. 문항·대본 승인 상태와 오디오 구간 상태는 독립적이다.
- `POST /api/questions/<id>/audio-segment`는 정확히 `version`, `start_ms`,
  `end_ms`, `status`를 받는다. `status`는 `candidate` 또는 `verified`이며,
  밀리초는 정수여야 하고 `0 ≤ start_ms < end_ms ≤ 원본 길이`를 만족해야 한다.
  서버는 0.5초 미만 및 10분 초과 구간을 거절한다. 출처 해시 불일치와 오래된
  버전 역시 저장을 차단한다.
- 25·26 / 27·28 / 29·30번은 하나의 대화를 공유한다. 한쪽에서 저장하면
  양쪽의 시간·상태·버전이 같은 트랜잭션에서 갱신된다. 대본·정답은 변경하지 않는다.
- `POST /api/questions/<id>/export-clip`은 빈 JSON 객체 `{}`를 받으며 **수동
  검증된** 구간만 내보낸다. 출처 파일 크기·해시를 다시 확인하고, 기존 클립을
  덮어쓰지 않으며, 같은 공통 대화의 두 문항에는 동일한 클립을 연결한다.

## 수동 검증과 회귀 테스트

검수자는 전체 음원에서 해당 발화를 처음부터 끝까지 듣고, 문제 번호 및 원본 듣기
대본·문항의 일치, 시작·종료가 발화를 자르지 않는지, 공통 대화가 빠짐없이 포함됐는지
각각 확인한 후에만 구간을 `verified`로 변경한다. 후보가 없거나 불확실하면
전체 음원으로 돌아가 수동 지정한다. 구간 수정 시 기존 검증과 내보낸 클립 연결은
무효화된다. 추출한 MP3에도 인코더 지연이 있을 수 있으므로 실제 결과를 다시 듣는다.

`tests/test_audio_segments_api.py`는 운영 DB를 SQLite 온라인 백업 API로
`TemporaryDirectory`에 복사하고, 해당 사본에만 스키마·음원 길이·구간을 기록한다.
임시 포트의 로컬 HTTP 서버를 통해 후보 저장, 시간 검증, 버전 충돌, 세 공통 대화
쌍의 원자적 동기화, Host/Origin/CSRF, 원본 SHA 변경 시 추출 거절을 확인한다.
내보내기는 인코더를 모의 구현하고 출력 경로를 임시 폴더로 바꾸므로 원본 MP3나
실제 파생 파일을 만들지 않는다. 이 테스트는 API 동작 검증이며, 내용 일치나
재배포 권한을 인증하지 않는다.
