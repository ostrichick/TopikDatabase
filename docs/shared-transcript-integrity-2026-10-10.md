35회 원본 SQLite의 세 쌍은 각각 같은 원본 대본 파일 ID·실제 페이지·문자 내용과 같은 MP3 asset, 후보 시작/종료·버전을 공유한다. 등록된 원본 PDF·MP3의 파일 크기/SHA-256 일치와 기존 기록은 읽기 전용으로 대조했다. **후보(candidate) 시각은 직접 청취로 검증한 확정 구간이 아니다.** 과거 frozen SQLite에는 여섯 문항 모두 `needs_manual_review`, 문항별 버전 2, 자동 생성된 검수 기록 두 건씩이었다.

반면 **현재 운영 PostgreSQL**의 실제 여섯 문항은 각 `question.review_status`와 `transcripts.review_status`가 모두 `verified`, 공유 대본 원본 ID·페이지·문자 내용은 쌍별 동일, 원본 오디오 구간은 모두 `candidate`였다. 문항당 `manual_question_review` 2건, `source_backed_correction_35` 1건 및 예전 자동 기록이 존재함을 SELECT로 확인했다. 이는 운영 DB를 수정하거나 청취 검증했다는 뜻이 아니다.

기존 `save_review()`는 검수자가 한 문항의 대본 텍스트를 수정하면 **선택한 question_id의 대본만 업데이트**했다. 짝 문항의 저장 버전과 승인 상태는 그대로였으므로 같은 대화 원본을 나타내는 저장 대본이 서로 달라져도 양쪽을 승인으로 표시할 수 있었다. 반면 공유 오디오 구간 저장은 정렬된 두 문항 잠금과 같은 경계 원자적 갱신을 수행했다. 동일한 저장 계약이 아니므로 **공유 음원 후보의 동일성, 대본 텍스트 변경, 인간의 개별 승인**을 별도 개념으로 다뤄야 한다.

## 구현된 원자적 보호와 검수 흐름

1. **일반 단독 대본 수정은 fail-closed 409:** 35회 등록된 세 쌍의 대본 텍스트가 바뀌는데 명시적 짝 문항 동의가 없으면, 해당 문항의 본문·선택지·승인·버전·검수 이력을 포함한 전체 트랜잭션을 롤백한다. 대본은 건드리지 않고 개별 문항만 수정·승인하는 종전 기능은 유지한다.
2. **명시적 공동 출처 정정:** 브라우저는 대본을 바꿔 저장할 때만 짝 문항의 현재 상세정보를 새 GET 1회로 조회하고, 동일 원본 대본인지와 짝 상태를 비교한다. 실물 PDF/음원 대조 근거를 메모에 적어야 하고 명확한 확인 대화상자를 승인해야 한다. 서버는 정확한 `shared_transcript` 필드에 짝 ID·짝 버전·명시적 출처 확인을 요구한다. 대본 출처 파일 ID·실제 PDF 페이지·기존 텍스트 일치, 선택 문항과 짝 문항의 독립 버전을 커밋 직전 재검사한다. 36회에는 이 규칙을 적용하지 않는다.
3. **승인 이력과 개인별 판정 분리:** 짝 문항이 이미 `verified` 또는 `rejected`라면 `confirm_reset_review:true`를 추가로 명시해야 한다. **과거 승인/반려 기록은 절대 삭제하거나 덮어쓰지 않고**, 원본 텍스트 수정으로 무효화된 짝 문항·대본의 현재 상태만 `needs_manual_review`로 변경한다. 선택 문항의 검수 결과만 선택한 상태로 저장하며 짝 문항이 자동 승인되는 일은 없다. 짝 문항 버전은 별도 `shared_transcript_source_correction` 기록으로 증가한다. 재검수되지 않은 짝 문항을 승인으로 보이게 하지 않는다.
4. **잠금·CAS·부분 실패 처리:** 중앙 PG 쓰기 계약의 두 문항 행 잠금은 ID 오름차순으로, 기존 음원 경계 잠금과 동일한 순서로 획득한다. 둘 중 한 버전이라도 달라지거나 원본이 이미 불일치하면 409로 실패하고 자동 재시도하지 않는다. 두 대본 수정·짝 검수 상태 갱신·양쪽 이력 기록은 한 트랜잭션에 속한다. PG 동시 쓰기 실측이 아닌 계약/가짜 PG SQL 잠금 순서 및 격리 SQLite 회귀로 검증한 범위는 구분해야 한다.
5. **UI·캐시·오류 복구:** 35회 공유 대본 안내 영역에서 짝 문항으로 키보드 접근 가능한 직접 이동을 제공하고 320/390px에서도 16px 읽기 텍스트·44px 이상 버튼을 유지한다. 공동 정정 ACK가 성공하면 짝 문항의 상세 캐시와 기존 bundle 슬롯을 무효화하고 짝 버전·검수 목록 상태만 갱신한 뒤 다음 문항을 불러온다. 정상 POST 1회, 명시적 공동 정정 전에 추가 GET 1회. ACK가 유실되거나 불분명한 경우 자동 재제출 대신 제출 초안을 보존하고 선택·짝 문항을 재조회해 결과를 재확인한다. 명백한 409는 초안과 현재 문항을 유지하고 원본·버전 비교를 요구한다. 기존 AI/빠른 목록/회차 격리·승인 후 이동은 유지했다.

**다음 최우선 과제:** 쓰기 권한이 있는 **완전 격리 PostgreSQL 테스트 서버의 신뢰성 있는 실행 환경**을 복구한 뒤, 공유 대본/음원 편집과 F3 bundle 동시 접근의 실제 PG 잠금·격리 수준·장애 복구를 브라우저까지 함께 재검증한다. 실제 운영 DB를 실험 용도로 사용하지 않는다. 그 뒤 실제 청취 담당자가 세 공유 후보 구간을 원음과 대조해 `candidate`→`verified` 승인할지 결정하는 별도 사람 검수 체계를 마련한다.
