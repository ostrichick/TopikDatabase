# TOPIK 35·36회 대본 화자 콜론 규칙 감사 (2026-10-11)

## 명세

- 듣기 대본에서 **화자명 뒤 공백 0개 + `:` + ASCII 공백 정확히 1개 + 대사**.
- 예: `가: 할말`, `나: 할말`, `철수: 대사1`, `영희: 대사2`, `남자: 안녕하세요.`.
- 여러 화자 줄 사이의 줄바꿈, 전체 대사, 어절, 원본 PDF와 음원은 변경하지 않는다.
- 줄 시작에서 확인된 화자 라벨만 변환한다. 시간 `12:30`, URL, 본문 속 콜론, `정답:` 등 메타데이터는 건드리지 않는다.
- 추출기에서 화자 시작 감지는 남자/여자 및 가/나/철수/영희 예제를 지원한다. 다른 라벨을 쓰는 미래 시험은 원문을 확인한 뒤 감지 대상을 확장한다.

## 기존 운영 DB 실측: READ ONLY

중앙 PostgreSQL을 읽기 전용 트랜잭션으로 검사했다. **아래 수치는 2026-10-11 조사 시점 기준으로, 배포·SQL UPDATE 여부를 의미하지 않는다.**

| 회차 | 대본 | 화자 턴 | 요구 규칙 위반 | 검수 상태 |
| --- | ---: | ---: | ---: | --- |
| 035-I-B | 30 | 85 | `035-I-L-001`의 2개 턴 (콜론 뒤 공백 없음) | 70문항 승인, 30대본 승인 |
| 036-I-B | 30 | 89 | 모든 30대본의 89개 턴 (`여자 :대사` 형식) | 15문항/15대본 승인, 55문항 대기 |

35회 SQLite 원본은 Stage 10 동결 자료로서 변경하지 않는다. 35회 중앙 DB의 원본 필드도 독립 AI 감사 소스 해시
`631c4fb71784439961956b582d0e66847eb862e2c2370f49c89d5ca520057c35`의 구성 요소다.
해당 원본을 직접 바꾸면 이전 감사·36회 마이그레이션의 고정 해시 검증을 깨뜨린다.

36회 운영 DB에는 v4→v5 이력만 존재하며 v5→v6 교정은 미적용이다. 승인된 `036-I-L-010` 대본에는
`그래요?그럼`→`그래요? 그럼` 인간 수정이 이미 있으므로 기존 v5를 무조건 적용하는 v6 마이그레이션은 차단되어야 한다.
과거 35회 감사와 36회 15건 승인 기록·현재 수정을 덮어써서는 안 된다.

## 이번에 반영한 코드와 후보

1. `src/extraction_rules.py`: 멱등의 `speaker-colon-v1` 정규화 함수. 대본 **줄 시작**에서만 동작한다.
2. `src/transcript_35.py`: 추후 PDF 대본 추출에서 같은 규칙을 적용한다.
3. `src/pdf_ingest_36.py`: 과거 감사 v4 재추출은 고정 원본과 동일하게 유지하고, 새 실행은 검증된 v6→v7 단계까지 추가한다.
4. `src/transcript_speaker_pipeline.py`: 36회 v6 원본 SHA·70문항·30대본·89화자·공유 대본 3쌍을 확인해 v7 후보를 생성한다. 원본 v4/v5/v6는 변경하지 않는다.
5. `scripts/import_exam_staging.py`: 새 v7을 가져오기 전 `speaker-colon-v1`을 검증한다. v5/v6 옛 계약을 변경하지 않는다.
6. `src/review_ui.py`: 원본 DB 텍스트와 별도로 화면용 **파생 대본 미리보기**를 새 규칙으로 표시한다. 사용자 편집란과 역사적 DB 원본은 자동으로 바꾸지 않는다.
7. `scripts/audit_speaker_db.py`: 운영 DB를 **READ ONLY**로 다시 점검하는 명령. 35/36회 원본·교정 후보의 각 SHA-256, 영향을 받는 문항 ID, 현재 검수 상태를 출력한다. `--apply` 기능은 없다.

실제 읽기 전용 SQL 감사에서 대상은 35회 `035-I-L-001` 1개와 36회 1–30번 30개였다.

생성된 파일은 Git 제외된 로컬 자료다.

| 파일 | SHA-256 |
| --- | --- |
| `topik-past-papers/derived/036-I-B/staging-v7.json` | `88a0fd177888d09523966e5a44938d374125d97218f85d222b263aed70a04db3` |
| `topik-past-papers/derived/036-I-B/speaker-diff-v6-v7.json` | `8b58ef1bb232c5f674b93c08537490e3fb0c7ddb65209a1d16ab3014411b8ac5` |

## 운영 DB 변경 보류 조건

오늘 기준 **15개 승인 이후의 새 백업과 별도 PostgreSQL 복원·무결성 검증 증거가 없다.**
따라서 운영 DB의 `transcripts.dialogue_text` 직접 UPDATE는 하지 않는다. 적용하려면 다음을 먼저 충족해야 한다.

1. 모든 PC의 현재 검수 편집·미저장 탭을 정리하고, 35회 동결 감사 보존 전략(버전별 파생 오버레이 또는 승인된 새 소스 스냅샷)을 결정한다.
2. 현재 DB의 SHA가 고정된 백업을 받아 격리 서버에 실제 복원하고 행·검수 이력을 비교한다.
3. 36회 10번 승인 수정을 보존한 정확한 per-cell 변경 목록과 35회 1번의 변경 2곳을 검증한다.
4. 원자적 잠금/compare-and-swap/복구 가능 트랜잭션과 신규 `import_metadata` 마커, **35·36 양 회차의 폼 버전 증가/409**를 구현·테스트한다.
5. 변경 후 원본 출처·정답·대본 공유 쌍·승인 이력·클립 참조를 비교해 변조가 없음을 입증한다.

미완료 작업을 완료로 주장하거나 역사적 독립감수 결과를 새 소스 버전의 승인 증거로 승격하지 않는다.
